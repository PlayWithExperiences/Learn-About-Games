# Devlog 002：M0 为什么从纵向切片开始

- 日期：2026-08-08
- 阶段：M0 已部署

> 2026-08-09 更新：本文保留 M0 当时的验证范围；当前产品边界与数据规模请看 [Devlog 003](/Learn-About-Games/devlog/2026-08-09-v02-knowledge-network/)。

## 为什么先做薄切片

Learn About Games 的正式第一版需要更多能力、学习路径、职业画像和资源。如果先把这些横向铺开，团队会很晚才知道数据模型、页面路径和视觉语义是否真的能支持学习。

M0 因此只选择一条完整路径：从首页认识地图，进入“迭代与验证”中的 Playtest，打开 Playtest 基础路径，最后抵达两条具体 Work Item。它很窄，但每一层都是真实内容，不用占位资源伪装覆盖规模。

## 这次验证了什么

- 新手能看见 9 个领域的地图骨架，并知道只有 Playtest 已有策展路径。
- 从业者能从能力和路径抵达具体视频与文章，不会停在频道或来源首页。
- 双语文章仍是一个 Work Item，通过两个可消费 access version 支持中文和英文筛选。
- `AAA · Game Designer` 画像只提供生产语境下的分类参考；个人学习状态独立保存在当前浏览器，不生成分数。
- Atlas 在同一产品内展示八类框架、Roguelike 种子、关系方向、证据状态和不确定性边界。
- Astro 静态构建、`/Learn-About-Games/` 子路径与 GitHub Pages workflow 可以一起工作。

## 刻意没有做什么

M0 没有扩展到 40-60 个节点、300 个候选资源、100 个已审核资源、10-15 条路径或 3-4 个画像，也没有加入账号、云同步、复杂搜索、力导图、自动因果推断或 Atlas 交互网络。这些工作需要新的内容扩展计划和真实使用反馈，不应由 M0 的技术骨架提前承担。

## 事故与教训

- Astro 会重写 Markdown 内部链接。站内文档链接需要显式映射到公开页面，非公开文件则指向仓库绝对 URL。
- Playwright 的 preview server 只预览现有 `dist`，不会自动 fresh build。先构建再验收，避免旧产物制造假 GREEN。
- 浏览器 history 与 bfcache 会恢复表单值，但脚本派生状态仍需在 `pageshow` 重放。资源筛选和职业透镜都必须覆盖这条路径。
- CSS 可以覆盖原生 `hidden`。依赖脚本的职业标签必须显式保证 hidden 状态，无 JavaScript 控件也不能假装可操作。
- Atlas 的时间排序不能暗示因果。关系需要锁定 from、to、type、status 与证据；方向箭头在桌面和移动端都必须清楚。
- GitHub Pages 的 build job 调用 `configure-pages` 时需要 `pages: read`。部署成功必须以 Actions run 与公开 URL 为证据，配置存在本身不算上线。

## 下一步

下一阶段先编写正式第一版的内容扩展计划，确定首批 40-60 个知识议题与能力节点、10-15 条学习路径，以及资源候选、审核和贡献闭环。Atlas 保留现有证据种子，复杂交互继续晚于核心地图与资源导航。
