- 日期：2026-08-08
- 发起品牌：PlayWithExperiences
- 项目仓库：https://github.com/PlayWithExperiences/Learn-About-Games
- 相关思考：[如何成为更好的设计师——三年来的视角转变](https://medill-east.github.io/2026/02/01/20260201-how-to-become-a-better-designer/)

## 1. 产品定义

Learn About Games 是一个公开的游戏知识地图、职业参考、学习资源导航与游戏创新沿革项目。

它不是资源黄页，也不是职业资格认证。产品用一张可讨论、可修订的通用地图回答三个连续问题：

1. 游戏设计及相关知识的全貌是什么？
2. 在特定职业与生产环境下，我大致处于哪里？
3. 如果我想补齐或探索某项能力，接下来可以学习和实践什么？
4. 某种游戏形式、机制或观念从哪里来，又如何演变成今天的样子？

产品的核心结构是：

> 知识与能力地图为学习主干，职业、生产环境、个人状态与资源为叠加层；Game Innovation Atlas 作为独立但互联的历史视图。

## 2. 背景与问题

公开的游戏学习资源分散在 YouTube、Bilibili、GDC、网站、播客、书籍、课程与学术出版物中。现有目录通常按媒介或来源组织，用户仍需自行回答“这个内容对我有什么用”。职业成长建议则常把个人经历或特定工作室的分工包装成可复制路径。

Learn About Games 要解决的不是“哪里有更多链接”，而是把单条内容精确连接到它能够帮助理解或训练的知识议题与能力，并保留来源、语言、版本、适用背景与推荐依据。项目还要让用户追溯游戏创新的出现、传播、变体、融合与复兴，同时把事实、推测和争议明确分开。

## 3. 目标与非目标

### 3.1 第一版目标

- 以 Game Design 为核心，覆盖通往 Creative Direction 所需的相邻能力。
- 为完全的新手提供认识全貌的入口。
- 为从业者提供按能力查找学习路径与高质量资源的入口。
- 支持 AAA、独立团队与个人开发等生产环境下的不同参考画像。
- 使用中文界面，同时完整描述中文、英文及其他语言的资源版本。
- 收录行业实践、案例、理论与相关学术研究。
- 建立 Game Innovation Atlas 的数据模型、页面入口和一条有证据的完整沿革样例。
- 允许公开贡献，所有公开推荐均经过维护者审核。
- 部署到 GitHub Pages，无需用户账号。
- 公开 Roadmap、Changelog 与里程碑 Devlog，让项目本身的发展可追溯。

### 3.2 第一版非目标

- 不完整覆盖程序、美术、音频等所有专业岗位的能力树。
- 不给用户、职业或资源生成单一总分。
- 不声称存在唯一职业路线或统一行业标准。
- 不建立账号、云同步、站内评论系统或完整 CMS。
- 不复制受版权保护的完整书籍、课程、字幕或文章。
- 不因追求资源总量而把“已抓取”伪装成“已推荐”。
- 不在第一版完整覆盖电子游戏史或建立所有创新的关系网络。

## 4. 设计原则

1. **地图不是答案**：地图是一个带出处、可修订的参考模型。
2. **语境先于标准**：职业能力画像必须声明其生产环境、团队规模与贡献者视角。
3. **单条内容连接能力**：GMTK 是来源，一期具体视频才是可学习的资源。
4. **资源服务于前进**：每项资源要说明它帮助理解什么、适合谁、如何使用。
5. **广度与可信度分层**：候选库可以快速增长，编辑精选必须经过审核。
6. **语言是版本关系**：原作、译本、字幕和转载必须保持关联，不能被当成无关条目。
7. **不同对象不共用含义**：领域、知识议题、能力、方法、角色和资源必须在数据与视觉上可区分。
8. **保存重要但暂不可访问的内容**：失效或付费资源可保留历史价值，但必须清楚标记。
9. **不制造虚假精确**：公开反馈是第三方证据，不等于客观质量分。
10. **相似不等于传承**：创新关系必须区分有证据的影响、结构相似、独立产生与争议假说。
11. **项目过程同样公开**：Roadmap 说明方向，Changelog 记录发布事实，Devlog 解释关键选择。

## 5. 用户与核心问题

### 5.1 新手探索者

需求：不知道游戏设计包含什么，希望看见全貌并获得起点。

核心入口：看地图。

### 5.2 有经验的从业者

需求：知道自己的兴趣、短板或目标能力，希望快速找到学习路径与具体资源。

核心入口：找位置、向前走、全局搜索。

### 5.3 职业目标探索者

需求：希望成为 Game Designer、Level Designer 或 Creative Director，但不了解不同环境下的能力组合。

核心入口：职业透镜叠加生产环境。

### 5.4 贡献者与维护者

需求：提交资源、修正元数据、补充语言版本、提出地图修订或提供专业审核。

核心入口：贡献指南、Issue 与 Pull Request。

### 5.5 游戏历史与创新探索者

需求：希望理解机制、形式、技术、界面、叙事或商业模式如何出现、分化、融合与复兴。

核心入口：Game Innovation Atlas 的时间轴、关系网络与证据页面。

## 6. 信息模型

### 6.1 地图对象

#### Domain（领域）

组织较大的知识空间，例如体验设计、玩法与挑战、叙事、制作与落地、迭代、领导与协作、产品与商业。

#### Knowledge Topic（知识议题）

描述值得理解但不必直接表述为“能做某事”的主题，例如玩家体验研究、游戏中的价值观、游戏伦理、程序修辞、游戏史和玩家动机。学术资源可以直接连接知识议题，也可以说明其如何支持某项能力。

#### Capability（能力）

描述能够通过实践逐步掌握的能力，例如体验解构、核心循环构建、节奏把控、Playtest 设计、反馈解释和愿景传达。

#### Practice（方法与实践）

描述培养或应用能力的行动，例如纸面原型、One-page Design、观察式 Playtest、访谈和数据分析。

### 6.2 语境对象

#### Role Lens（职业透镜）

Game Designer、Level Designer、Creative Director 等角色。角色本身不拥有独立知识树，而是为现有能力赋予不同的重要性、建议深度与责任范围。

#### Production Context（生产环境）

第一版至少区分：

- 大型或 AAA 团队
- 中小型团队
- 独立团队
- 个人开发者

职业透镜必须与生产环境共同使用。例如“AAA / Game Designer”和“Solo / Independent Creator”是不同的参考画像。

画像表达三个维度：

- 建议深度
- 建议广度
- 责任范围：亲自执行、能够协作、能够判断或能够指导

第一版只策展少量有依据的组合，不生成完整的“角色 × 团队规模 × 职级”矩阵。

### 6.3 资源对象

#### Source（来源）

创作者、组织、频道、出版社或网站，例如 GMTK、GDC、樱井政博、白金工作室。

#### Collection（系列）

播放列表、课程、丛书、专题或播客系列。

#### Work Item（单项内容）

一期视频、一场演讲、一篇文章、一本书、一篇论文或一集播客。单项内容是能力关联的默认粒度。

#### Segment（内容片段）

视频时间戳、书籍章节、论文部分或课程单元。只对重点资源细分，不要求所有候选资源都达到片段级。

#### Edition / Access Version（版本与访问形式）

描述同一作品的原作、译本、字幕、配音、再版或合法访问入口。版本必须记录：

- 原作语言
- 当前版本语言
- 字幕或配音语言
- 官方翻译、社区翻译或机器翻译状态
- 出版或发布信息
- 免费、付费、订阅或地区限制
- 原作与其他版本的关系

#### Capability / Topic Link（能力或议题关联）

每条关联记录：

- 主要关联或辅助关联
- 内容具体解释或训练什么
- 在学习路径中承担的作用
- 推荐章节或时间戳
- 推荐理由、适用基础与局限

同一内容只存一份，可以关联多个能力和知识议题。

### 6.4 学习与个人对象

#### Learning Trail（学习路径）

一条路径包括：

1. 能力或议题为何重要
2. 建议前置内容
3. 核心概念与常见误区
4. 高质量案例
5. 按作用组织的资源
6. 实践练习
7. 自我检验方式
8. 后续延伸方向

#### Personal State（个人状态）

用户可以为能力标记：

- 尚未接触
- 理解概念
- 做过练习
- 在真实项目中使用过
- 能够指导或评审他人

状态只保存在浏览器本地，不进入公共地图，也不汇总成职业能力总分。

### 6.5 Game Innovation Atlas 对象

Game Innovation Atlas 是独立于能力地图的历史视图。两个视图可以通过游戏、知识议题和资源互相连接，但不能混成同一种节点。

#### Innovation（创新）

描述可追踪的游戏机制、形式、技术、界面、叙事、视听、社交、发行或商业创新。创新可以有多个先驱、变体和后继，不假设单一父节点。

#### Game Artifact（游戏作品）

描述体现、尝试、推广或改造某项创新的具体游戏。作品不是创新本身；同一作品可以承载多项创新，同一创新也可在多个地区独立出现。

#### Innovation Relation（创新关系）

第一版允许的关系类型包括：

- 最早有证据的实例
- 直接影响
- 变体或分支
- 融合
- 复兴或重新流行
- 平行或独立产生
- 结构相似但影响未知
- 存在争议

每条关系必须声明方向、关系类型、证据状态和说明。没有出处的视觉连线不得作为事实发布。

#### Innovation Evidence（创新证据）

证据可以来自开发者访谈、设计文档、论文、专利、同期报道、可信历史著作或可核查的作品内容。证据状态至少区分：

- 已证实
- 较可信
- 推测
- 存在争议

“第一款游戏”统一表述为“当前数据库中最早有证据的实例”，除非来源足以支持更强结论。

该模块借鉴 Carnegie Mellon University Entertainment Technology Center 的 [Game Innovation Database](https://www.cmu.edu/homepage/innovation/2007/spring/gaming-firsts.shtml) 对创新关系与公众贡献的探索，也借鉴 Maastricht University [Digital Ludeme Project](http://ludeme.eu/project/) 对游戏组成单元、传播与历史不确定性的处理。

## 7. 关系与不变量

- 领域包含知识议题、能力与方法。
- 能力之间可以存在前置、组成、互补和延伸关系。
- 方法可以培养或应用一个或多个能力。
- 职业画像只能高亮已有能力，不复制一棵新的角色知识树。
- 职业画像必须声明生产环境、依据、贡献者背景、争议和审阅时间。
- 资源必须连接单项内容或片段，来源与系列只负责聚合。
- 媒介、语言、费用和平台是筛选维度，不是知识树主干。
- 资源数量不能用于表示能力的重要性。
- 学术研究可以连接知识议题或能力，但不能被强制改写成生产技能。
- 游戏作品、创新与创新关系必须是独立对象。
- 创新关系必须至少连接一项证据；“结构相似”不能自动升级为“直接影响”。
- 存在不确定日期时保留日期范围，不能为了画出整齐时间轴伪造精确年份。

## 8. 核心用户旅程

### 8.1 看地图

用户从全貌进入领域，再进入知识议题或能力。系统始终显示当前位置、上级路径和回到全貌的入口。

### 8.2 找位置

用户选择职业目标与生产环境，获得“核心、重要、建议了解”的地图高亮；随后叠加自己的实践状态，看到差异与可选方向。结果是参考分布，不是评价分数。

### 8.3 向前走

用户选择感兴趣或需要补齐的能力，进入策展过的学习路径；路径提供理解、案例、资源、练习和自我检验，而不是一组无序链接。

### 8.4 直接查找

全局搜索同时返回：

- 能力与知识议题
- 学习路径
- 单项资源与重点片段
- 职业画像
- 来源与系列

例如搜索 Playtest，应能直接到达相关能力、Valve 案例视频、书籍章节和练习，而不是要求用户先进入 GMTK 频道自行寻找。

### 8.5 追溯创新

用户从一项创新或一款游戏进入，沿时间轴查看已知先驱、关键推广者、分支、融合和复兴；切换到关系网络后查看跨时期与跨品类连接。每条连线都可以展开证据、置信状态和争议说明。

## 9. 页面结构

- 首页：品牌主张与“看地图 / 找位置 / 向前走”入口
- 能力地图
- 能力或知识议题详情
- 学习路径
- 职业与生产环境画像
- 资源库
- 单项资源详情
- 来源与系列页面
- Game Innovation Atlas
- 创新、游戏与证据详情
- 贡献指南与方法论
- Roadmap、Changelog 与 Devlog

## 10. 地图与视觉语义

- 默认只展示领域与主要知识议题或能力，避免把资源全部铺进地图。
- 点击领域逐层展开，点击节点在侧栏显示解释、路径和精选资源。
- 职业重要性、个人实践状态和审核状态必须使用不同的视觉编码。
- 每种形状、颜色、位置和连线只表达一种稳定含义。
- 节点大小不代表资源数量或能力价值。
- 桌面端提供地图；移动端使用可展开大纲与卡片，不缩小整张图。
- 第一版不采用无约束的力导向关系图，优先保证方向感与可解释性。
- Game Innovation Atlas 使用时间轴与关系网络两种互补视图；能力地图的视觉语义不复用于创新网络。
- 创新连线的样式必须区分已证实、推测和争议，不能让所有关系看起来同等可靠。

## 11. 资源策展与证据

### 11.1 审核状态

1. 已收录：确认存在并具有基本元数据
2. 已归类：连接到能力或知识议题
3. 已审核：检查内容并补充适用范围、推荐理由与局限
4. 编辑精选：进入重点能力页或学习路径
5. 已归档：失效、过时或存在版权问题，但保留历史信息

### 11.2 推荐依据

每项重点资源可以展示：

- 维护者评价
- 学习者公开反馈摘要
- 专业人士、课程或阅读清单引用
- 公开平台反馈
- 第一手经验、案例、练习等内容属性
- 有代表性的批评与局限
- 采样日期与原始来源链接

第一版使用人工整理的公开反馈摘要，不实时聚合不同平台的数据，也不生成跨平台质量分。

### 11.3 学术资源元数据

论文、学术专著与研究报告除通用字段外，可以记录：

- 作者与机构
- 期刊、会议或出版社
- DOI 或稳定标识符
- 发表年份
- 同行评审状态
- 研究方法
- 开放获取状态
- 对能力或知识议题的相关性说明

第一版优先收录与 Game Design、玩家体验、设计方法和 Creative Direction 相邻的研究；未来再扩展更广泛的 Game Studies。

## 12. 多语言策略

- 第一版界面为中文。
- 所有界面文案从第一天起使用可国际化结构。
- 数据支持中英文名称和描述，并允许其他语言版本。
- 用户可以按“我能阅读或观看的语言”筛选，而不只按原作语言筛选。
- 后续提供完整中英双语界面，不需要迁移现有资源数据。

## 13. 数据规模与覆盖策略

采用“较大的候选库 + 重点审核核心内容”的两层策略。

第一版发布基准：

- 40–60 个知识议题与能力节点
- 300 个以上候选资源
- 至少 100 个完成审核
- 10–15 个重点节点具有完整学习路径
- 中文与英文筛选都能返回有意义的内容
- 3–4 个职业与生产环境参考画像
- 1 条端到端 Game Innovation Atlas 垂直样例，包含创新、游戏、关系、证据、时间轴和网络视图

覆盖质量同时检查媒介、语言、难度、免费与付费、理论与实践、概念与案例、学习与练习。总数不替代覆盖率。

## 14. 技术架构

### 14.1 技术栈

- Astro
- TypeScript
- 结构化内容与构建期 Schema 校验
- Markdown 内容页面
- 局部客户端交互组件
- 静态搜索索引
- 浏览器 localStorage
- GitHub Actions
- GitHub Pages

Astro 负责生成静态页面；只有地图、搜索、筛选与个人进度加载必要的客户端 JavaScript。

### 14.2 GitHub Pages 约束

目标项目站点地址形如：

`https://playwithexperiences.github.io/Learn-About-Games/`

构建必须正确配置站点 URL 与 `/Learn-About-Games/` 基础路径。页面链接、静态资源、搜索索引和客户端路由都要在该子路径下测试。

### 14.3 部署

合并到 `main` 后由 GitHub Actions：

1. 安装依赖
2. 校验内容 Schema 与关系不变量
3. 运行测试
4. 构建静态站点
5. 上传并部署到 GitHub Pages

## 15. 数据与贡献流程

数据流：

> 公开来源 → 候选资源 → 元数据规范化 → 去重与版本关联 → 能力或议题归类 → 人工审核 → 静态构建 → 用户搜索与学习

社区通过 Issue 或 Pull Request：

- 提交新资源
- 修正失效链接和元数据
- 增加语言版本
- 补充推荐依据或反面意见
- 提议地图节点或关系变更
- 提交创新实例、历史来源或关系反证

自动检查负责格式与引用完整性；维护者负责分类判断、版权风险与是否进入编辑精选。

## 16. 失败处理

- 外部链接失效：保留条目、标记检查日期，并关联替代入口。
- 未审核资源：可进入资源库，但不能显示为编辑精选。
- 翻译信息不完整：只展示已确认信息，不推断不存在的版本。
- 重复转载：优先作者、版权方或出版方的合法原始来源。
- 有争议内容：展示带出处的不同观点，不以单一评分覆盖。
- 创新关系证据不足：降级为推测、相似或争议，不显示为确定影响。
- 日期存在冲突：保留来源与日期范围，禁止静默选择更方便展示的年份。
- 内部关系错误：构建失败，阻止部署。
- localStorage 数据损坏或版本不兼容：回退到安全空状态，并提供导出、导入与清除。
- 外部链接检查受网络波动影响时：报告问题但不因一次超时删除资源。

## 17. 测试与验收

### 17.1 自动检查

- ID 唯一性
- 能力、议题、来源、版本与路径引用完整性
- 原作与译本关系有效性
- 必填语言与访问字段完整性
- 重复 URL 与明显重复内容
- 学习路径无断链
- 静态构建与 TypeScript 检查
- GitHub Pages 基础路径正确性
- localStorage Schema 与迁移测试
- 创新关系类型、证据引用与日期范围完整性
- 确定性影响关系不存在无解释的时间倒置

### 17.2 关键用户旅程

- 新手能从首页进入地图并理解主要领域。
- 用户能选择职业与生产环境透镜。
- 用户能从能力节点直接进入具体单项资源。
- 用户能按语言、媒介、难度和访问条件筛选。
- 用户能保存个人能力状态，刷新后仍然存在。
- 手机端能以大纲形式完成同等导航。
- 搜索能够同时发现能力、议题、路径和单项内容。
- 网站在 `/Learn-About-Games/` 下无断裂页面与资源。
- 用户能完成一条创新沿革样例的时间轴与关系网络探索，并查看每条关系的证据状态。

## 18. 品牌关系

- PlayWithExperiences 是发起者、策展者与长期母品牌。
- Learn About Games 是面向公众的具体产品。
- 品牌表达应同时服务个人持续学习与公共知识贡献，避免把个人观点包装成唯一权威。
- 项目通过公开 Roadmap、Changelog 与 Devlog 展示自身的来源、变化和未来方向。
