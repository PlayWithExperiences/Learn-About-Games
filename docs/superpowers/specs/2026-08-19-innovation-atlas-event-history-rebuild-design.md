# Innovation Atlas 事件史主图重构规格

**日期：** 2026-08-19  
**状态：** 已确认方向，待按本规格实施

## 1. 目的

Innovation Atlas 要回答的核心问题不是“哪些游戏按年份出现”，而是：

> 某种设计观念、机制、技术或生产方式，何时被提出、如何被转译、怎样扩散，并对后续游戏造成了什么可核验的影响？

因此主叙事对象是 `Innovation Event`。游戏、硬件和实验程序是承载这些事件的历史证据；品类是观察和高亮的透镜，不是彼此隔离的子图。

## 2. 核心对象与关系

继续使用现有 `atlasNodes`、`atlasRelations`、`atlasEvidence` 和 `atlasThemes`，不恢复已退休的 Domains / mapGroups ontology。

### 节点

- `innovation`：可被来源支持的设计事件、机制引入、形式转译、技术条件或品类形成节点。事件名称描述“发生了什么变化”，不以作品名命名。
- `game`：承载、实现、传播或重新组合事件的作品。它可以承载多个事件，但不等同于任何一个事件。
- `category`：有明确时间范围的类别形成或命名语境。
- `experimental-*` / `commercial-hardware`：历史基础对象，只有在证据关系中有作用时才进入主图。

事件继续使用 `definition`、`mechanism`、`transformation`、`diffusion` 四种角色。角色表示事件在路线中的功能，不表示价值排名或唯一历史起点。

### 关系

- `evolution`：事件到事件的演进主线，说明一个设计问题、机制或形式怎样被后续事件重新组织。
- `carrier`：事件到作品／硬件／实验对象的承载关系，说明作品如何让事件变得可观察。
- 其他关系类型继续表达 direct influence、design response、prototype-to-product、fusion、parallel origin 等更具体的证据语义。

每条关系必须有方向、状态、摘要和至少一条 Evidence。日期相邻、名称相似或同属一个品类不能自动生成影响关系。

## 3. 全局图与两种视角

页面只保留一张全局节点与关系网络。选择品类或 Genre Family 时：

- 不隐藏其他品类的节点、关系或跨品类边；
- 只提高匹配事件、其演进路径和直接承载作品的强调度；
- 说明当前是“高亮透镜”，不是独立发展史；
- 选择空透镜时保留全图，并显示该透镜暂无达到证据门槛的事件。

地图提供两个互斥但共享同一数据和坐标语义的视角：

1. **代表作品**：作品是主要可见节点，适合从作品进入历史；创新事件作为较高强调的关系标记和详情入口。
2. **创新事件**：创新事件沿中央时间带从左到右排列，事件—事件关系成为主线；作品、硬件和实验对象位于事件附近的证据层，默认较小、较轻，仅在事件详情或显式展开时强调。

切换视角不复制数据、不创建第二张隔离地图，不改变节点 ID、关系 ID、年份或全局关系集合。品类透镜在两个视角都只负责高亮。

## 4. 事件视角的布局语义

- 中央主带是事件层，不再把事件固定在画布最上方的独立 lane。
- 事件层按 `startYear` 从左向右排列；同年事件按稳定 ID 排序，避免输入顺序漂移。
- `evolution` 关系从事件节点边界出发，形成可读的主线路由；主线不穿过其他节点。
- 承载作品层位于事件主带上下的次级区域，使用较小卡片和较弱边框；`carrier` 关系使用低强调线，不与演进主线争夺视觉优先级。
- 类别范围条和证据索引不再占据事件主线的上方空间；它们作为辅助标注或详情内容出现。
- 事件节点、作品节点、类别范围和实验对象必须使用可解释且不混淆的形状／线型。
- 1440、1024、320 和 no-JS 都必须保留事件→作品→证据的层级顺序；窄屏使用可展开的原生事件大纲，不把整张桌面图压缩成不可读缩略图。

## 5. 事件详情

点击事件节点打开同一页面内的原生详情层，内容顺序固定为：

1. 事件名称、年份／范围和事件角色；
2. 机制说明：它解决了什么设计问题，新增了什么可行性；
3. 前置事件、后续事件和跨品类影响；
4. 承载作品／硬件／实验对象（可链接到各自详情）；
5. Evidence、来源、定位信息、证据状态和范围边界。

再次点击当前事件、Escape、关闭按钮或从详情返回，都应回到图中原位置并恢复焦点；不能要求用户只能点击“返回全图”才能撤销选择。打开详情不能推动主图产生大幅布局跳动。

## 6. 第一阶段内容目标

先用四条互相连接的主线验证模型，而不是继续平均堆叠作品：

- FPS：第一人称空间、连续移动、武器反馈、垂直空间、网络／情境叙事；
- RPG／角色成长：角色属性、持续进展、战斗与成长的组合转译；
- RTS：资源／基地／实时生产、单位调度、阵营差异与反制；
- 开放世界／动作冒险：空间探索、目标锁定、非线性路线和系统交互。

第一阶段验收目标：

- 至少 24 个事件节点，覆盖上述四条主线；
- 每个事件至少 1 个可达承载对象，且每个事件有 Evidence 闭包；
- 至少 16 条有来源支持的事件—事件演进关系；
- 至少 4 条跨品类关系可在全局图中被看见并被透镜高亮；
- FPS 先做成从定义／机制到转译／扩散的完整示范，其余三条按同一数据契约迁移；
- 所有“第一”“发明”“直接影响”等强结论必须由来源明确支持，否则改写为范围受限的形成、承载、响应或可信关系。

事件数量不是质量分，也不自动产生学习顺序、职业适配或重要性排名。

## 7. 数据研究与补全边界

研究优先使用开发者访谈、设计文档、原始项目记录、博物馆／档案馆记录、论文、同期报道和官方回顾。搜索摘要、聚合目录、无法访问的登录页不能作为事件证据。

新增事件必须同时记录：稳定 ID、中文／英文名称、年份或范围、角色、机制说明、主题透镜、证据 ID。新增关系必须记录关系类型、状态、方向、摘要和证据。作品只在来源或作品事实能支撑其承载作用时挂到事件上，不因“看起来属于该品类”自动挂接。

## 8. 非目标

- 不把 Innovation Atlas 变成作品评分、排名或“最佳游戏”榜单。
- 不用时间相邻、品类标签或模型常识替代影响证据。
- 不将一个品类复制成一张孤立地图，也不删除全局跨品类关系。
- 不在本阶段引入账号、社区投票、自动生成历史因果或后端 CMS。

## 9. 验收与风险

### 功能验收

- 代表作品／创新事件视角共享完整节点与关系 ID 集；
- 事件视角的中央事件主带位于主图核心区域，而非顶部附加索引；
- 选择任一品类只改变高亮，跨品类关系仍可见；
- 点击事件可见机制、演进关系、承载作品和证据，并可用再次点击／Escape／关闭返回；
- 无 JavaScript 时事件层级和证据链接仍可读，禁用控件有说明。

### 质量验收

- `npm run check`、全量 Vitest、fresh `npm run build` 和 Atlas 双视口 E2E 通过；
- Light/Dark、1440/1024/320 无横向溢出；事件标题不出现被截断或只剩一两个字的孤立行；
- 事件主线和承载层零碰撞，所有关系端点命中对应节点边界；
- 证据、节点、关系和透镜引用闭包通过构建期校验。

主要风险是历史材料常把“最早实例”“直接影响”和“后来形成的类别名称”混在一起。实现必须保留不确定性和证据状态，宁可暂缺事件，也不能用一个看似完整但无法核验的谱系填空。
