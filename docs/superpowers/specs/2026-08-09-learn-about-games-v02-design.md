- 状态：已由发起人确认，直接进入实施
- 日期：2026-08-09
- 基线：已部署 M0 `373ef17bbcc7646e8b5183d300a7a394fe15e0ae`
- 发起品牌：PlayWithExperiences
- 项目仓库：https://github.com/PlayWithExperiences/Learn-About-Games
- 前一版设计：[2026-08-08-learn-about-games-design.md](2026-08-08-learn-about-games-design.md)

## 1. 本轮要解决的问题

M0 证明了静态内容契约、多语言访问版本、职业参考、本地个人状态、创新证据和 GitHub Pages 部署可以走通，但它仍是纵向切片，不是可长期使用的产品。

v0.2 直接修复五个可观察的问题：

1. 能力地图是两列卡片排版，没有位置、区域与连接关系，像便当盒而不像地图。
2. 唯一职业画像只在卡片底部增加小字，用户无法感知它如何改变观察方向。
3. 资源库只有两条 Playtest 内容，且“审核、精选、学习路径”语义需要维护者作强判断，无法支撑开放扩充。
4. Innovation Atlas 把时间顺序、关系与证据拆成三个列表，七条关系无法被读成一张演变网络。
5. 一级导航混合核心功能与项目治理资料，且全站只有一套颜色主题。

## 2. v0.2 产品承诺

v0.2 是第一版具备实际内容密度的公开知识产品。它回答四个问题：

1. 游戏设计及相邻知识的全貌是什么？
2. 某种职业与生产环境通常会关注哪些能力？
3. 针对某项能力或议题，我能找到哪些具体学习资源？
4. 游戏中的创新、形式与品类如何随时间产生联系和变体？

它仍然不是职业认证、课程体系、资源排行榜或电子游戏史的标准答案。

## 3. 一级信息架构

中文界面使用：

1. 能力地图
2. 职业方向
3. 成长资源
4. 创新变迁
5. 关于本项目

对应英文名称固定为：

1. Expertise Map
2. Career Lenses
3. Learning Resources
4. Innovation Atlas
5. About

中文界面不需要同时挤入两套标签。英文名称进入国际化字典，为完整英文界面保留稳定术语。

Roadmap、Changelog、Devlog、Methodology、Contributing 与项目说明全部收进“关于本项目”，不再作为一级导航项。旧公开 URL 保持可访问。

首页保留三条主要行动：看全貌、从职业语境找方向、按主题寻找资源。Innovation Atlas 是独立的历史探索入口。

## 4. 能力地图

### 4.1 稳定对象

- **Domain**：知识地域，例如体验设计、系统设计、研究验证、生产协作。
- **Capability**：能够通过实践逐步掌握的能力。
- **Knowledge Topic**：值得理解但不必伪装成生产技能的议题，学术研究可以直接连接它。
- **Capability Relation**：能力之间有明确含义的关系。

Practice 暂时作为能力详情中的方法内容表达。只有在真实数据证明需要独立检索时，才升级为独立地图节点。

### 4.2 关系类型

地图只公开三种关系：

- `belongs-to`：Domain 包含 Capability 或 Knowledge Topic，由对象的 `domainId` 表达。
- `supports`：掌握或练习 A 经常有助于 B，但不把 A 写成强制先修课。
- `complements`：A 与 B 经常协同使用，关系不表示顺序。

不使用“必修”“唯一前置”“标准成长路线”等措辞。每条 `supports` 与 `complements` 关系必须有简短说明，不能仅为让图更密而连线。

### 4.3 空间语义

桌面地图是一张稳定的知识地域图：

- Domain 是有名称的地域。
- 所有 Domain bounds、Capability 锚点和 Knowledge Topic 锚点使用同一张 0-100 全局坐标系；构建时验证节点锚点落在所属 Domain 内。
- Capability 使用统一的圆角节点标签。
- Knowledge Topic 使用不同轮廓与明确的“议题”标签。
- `supports` 使用带方向的连线。
- `complements` 使用无方向的虚线。
- 节点位置只表达领域归属和知识邻近，不表达价值、难度、资源数量或职业重要性。
- 节点大小固定，不随资源数量变化。

点击节点进入统一详情页，查看定义、相邻关系、相关资源和个人实践状态。所有节点都可进入，不再由是否存在 Learning Trail 决定可点击性。

移动端不缩小桌面图。它按 Domain 展示可展开的大纲，并在每个节点下列出相同的关系信息。

### 4.4 首轮内容规模

- 约 8 个 Domain
- 36-42 个 Capability
- 8-12 个 Knowledge Topic
- 50-80 条有明确说明的关系

首轮重点仍是 Game Design 及通往 Creative Direction 的相邻能力，不冒充程序、美术、音频等专业的完整能力地图。

## 5. 职业方向

### 5.1 定义

Career Lens 是对同一张能力地图的参考高亮，不复制角色专属知识树，不规定学习顺序，也不计算匹配度。

命名格式固定为：

> Production Context · Role

首轮目标：

- `AAA · Game Designer`
- `AAA · Creative Director`
- `Indie · Solo Developer`

### 5.2 可见影响

职业方向页展示可选择的参考画像。应用画像后：

- 地图保留全部节点。
- 画像覆盖的能力以“核心、重要、建议了解”三档描边和文字标签高亮。
- 未覆盖节点降低视觉强调但不隐藏。
- 旁侧摘要按三档列出能力、责任范围和已有相关资源数量。
- 点击摘要项聚焦对应节点并提供进入详情的链接。

三档只表示该公开画像中的关注程度，不表示个人分数。个人实践状态继续使用独立标记和本地存储，不与职业画像合并成差距、百分比或职业适配判断。

### 5.3 依据与边界

每个画像必须记录：

- 角色和生产环境
- 依据说明与公开来源
- 能力关注程度
- 责任范围：亲自执行、协作贡献、判断或指导
- 适用边界与争议
- 最近复核日期

数据契约使用受限枚举：关注程度只能是 `core | important | suggested`，责任范围只能是 `execute | contribute | decide | direct`。公开依据保存为可点击的 `basisLinks`，每项包含标题、URL 与来源说明；`reviewedAt` 使用 ISO 日期。画像投影只能返回节点 ID、关注程度、责任范围和展示分组，不允许派生分数或读取个人实践状态。

若依据不足，宁可减少能力标注，也不填满一个看似精确的多边形。

## 6. 成长资源

### 6.1 不再以学习路径为核心

v0.2 不把 Learning Trail 作为主要产品对象。不同人的经验、目标和时间不同，平台不声称存在统一学习顺序。

M0 的 Playtest Trail 改为“Playtest 主题资源集合”。它可以包含概念提示、练习建议和相关内容，但没有强制顺序，也不决定资源能否进入能力页。

旧 Trail URL 保留兼容跳转，避免公开链接突然失效。

### 6.2 不设置站内质量等级

资源库不再显示候选、已审核、精选、星级、评分、排名或推荐强度。收录表示项目确认该条目存在，并认为它和某个主题或能力相关，不表示统一质量认证。

每项资源展示可核查事实：

- 标题、作者或 Source
- 单项内容类型
- 相关 Capability 与 Knowledge Topic
- 为什么与该主题相关
- 原始语言与可消费语言版本
- 免费、付费、订阅或地区限制
- 链接检查日期
- 可选的外部评价事实

外部评价必须保留提供方、原始指标或原文摘要、样本量或计数（若有）、采集日期和来源链接。不同平台的数据不归一化，不合并为站内分数，也不据此自动排序。

### 6.3 Source 与 Work Item

Source 是创作者、频道、组织、出版社或网站，例如 GMTK、GDC、樱井政博、白金工作室与 Level Design Book。Source 记录实体类型、简介、主页、常用语言和可选外部观察。Source 作为独立结果在资源库中被发现，并拥有聚合其 Work Item 的详情页。

Work Item 是一期视频、一场演讲、一篇文章、一本书、一篇论文、一集播客或一门具体课程。每项 Work Item 保存稳定的 canonical identity URL，并可追溯到 Source。能力关联默认达到 Work Item 粒度；有价值时继续细化到章节或时间戳。

同一作品只存一份，通过 Access Version 记录原版、译本、字幕、配音和合法访问入口。

### 6.4 浏览与筛选

资源库先按主题和能力组织，再提供事实性筛选：

- 能力或知识议题
- 媒介
- 可消费语言
- 访问模式：免费、付费或订阅
- 可选的地区限制
- 原始版本与翻译版本
- Source

无 JavaScript 时仍列出全部资源并保持链接可访问，依赖脚本的筛选控件必须禁用并说明。

### 6.5 首轮内容规模

v0.2 目标收录约 100-150 项真实资源，至少覆盖 12 个核心主题。数量是发布目标，不是为了让构建通过而填充或删除数据的硬上限。硬性验收是每项具有唯一 canonical identity、真实 Source、至少一个已核查 Access Version、基本元数据和明确主题关联。

首轮优先包含用户明确提到的 GMTK、GDC、樱井政博、白金工作室 Bilibili 内容、Level Design Book、Will Wright MasterClass、游戏设计书籍、播客与学术研究，并继续寻找同等级的公开来源。

## 7. Innovation Atlas

### 7.1 一个全局时间网络

Innovation Atlas 不再按主题裁出孤立子图。所有公开节点和关系存在于同一张横向时间网络中：

- 横轴只表达时间。
- Game 节点使用明确发行年份。
- Innovation 与 Category Formation 可以使用年份范围。
- 纵向位置用于实体类型分层、主题邻近和避免碰撞，不表示价值排名。
- 时间相邻不自动产生连线。

节点类型至少包括：

- Game
- Innovation
- Category Formation

三种实体必须使用不同且可解释的形状。Evidence 不作为同层历史节点，而在节点或边的详情中以文献条目呈现。

### 7.2 关系与证据

关系类型包括：

- 直接影响
- 变体或分支
- 融合
- 复兴或重新流行
- 平行或独立产生
- 结构相似但影响未知
- 存在争议

关系明确区分方向性：直接影响、变体、融合与复兴通常有向；平行产生与结构相似默认无向；争议关系必须显式声明有向或无向。每条边都显示方向性、类型、证据状态与证据入口。关系证据不足时降低为相似、推测或争议，不用确定性动词。

### 7.3 主题透镜

Roguelike、Metroidvania、关键词或品类只是同一网络的高亮透镜。Atlas 使用一份统一标签 taxonomy；Node、Relation 与 Theme 都只能引用其中的标签：

- 未选择主题时显示完整网络。
- 选择主题后，高亮相关节点和边。
- 非相关上下文降低强调但保持可见。
- 选择主题不改变节点和关系总数。

首轮至少发布 Roguelike 与 Metroidvania 两个透镜，整体目标为 25-40 个节点和 15-25 条有证据关系。Metroidvania 不争夺“第一款”的简单结论，而区分命名史、机制结构、直接影响、融合和后来的类别形成。

### 7.4 交互

- 点击节点查看简介、时间、相关主题、前序与后续关系。
- 点击边查看关系说明、证据状态和来源。
- 主题按钮只执行高亮，不隐藏网络。
- 移动端按时间段和关系分支展开，保持与桌面图等价的关系语义。

## 8. 颜色主题与视觉系统

全站提供三种外观模式：跟随系统、浅色、深色。

- 默认跟随 `prefers-color-scheme`。
- 用户主动选择后存入当前浏览器。
- 页面加载前应用已保存选择，避免明显闪烁。
- localStorage 损坏或未知值时回退到跟随系统。
- 无 JavaScript 时仍跟随系统偏好。
- 浅色与深色使用相同的信息层级、地图语义和可访问名称。

主题控件位于顶部工具区，不占一级导航项。地图关系、职业关注程度和实体类型不能只依赖颜色，还要同时使用形状、线型、边框或文字标签。

完整视觉 token 和组件约束记录在仓库根目录 `DESIGN.md`。

## 9. 数据模型调整

### 9.1 新增

- `knowledgeTopics`
- `capabilityRelations`
- `resourceTopics`
- Source 的类型、简介、主页、语言与外部观察字段
- Resource 的 canonical identity URL、`resourceTopicIds`、`knowledgeTopicIds`、`whyRelevant`、原始语言与可选外部观察
- Access Version 独立的访问模式与地区限制
- Role Profile 的公开依据链接、复核日期，以及受限的 priority/responsibility 枚举
- Atlas Node 的 `kind` 扩充到 `game | innovation | category`
- Atlas Node 的年份范围
- Atlas 的统一标签 taxonomy；Node、Relation 与 Theme 都引用它，Theme 不再拥有子图

### 9.2 移除或降级

- 移除 `resources.reviewStatus`
- 移除 Learning Trail 作为核心 catalog 与能力详情入口条件
- 移除 `atlasThemes.nodeIds` 与 `relationIds`
- 移除 MapExplorer 中只允许 Playtest 点击的硬编码
- 移除用户可见的“已审核、已策展、候选、精选”状态

### 9.3 构建期不变量

- 同一 collection 内的 ID 唯一；跨 collection 的公开引用使用实体类型确定目标，不把同名 Resource Topic 与 Knowledge Topic 当作同一对象。
- Domain、Capability、Knowledge Topic、Source、Resource、Role Profile、Atlas Node、Relation 与 Evidence 引用完整。
- Capability Relation 的两端必须都是 Capability，不连接 Knowledge Topic；不允许自环，类型必须来自受限枚举。
- Resource 至少连接一个 Capability、Knowledge Topic 或 Resource Topic。
- Work Item canonical identity URL 唯一，Source 引用存在；Access Version 至少一项，URL、语言、访问模式、可选地区限制和检查日期完整。
- External Signal 必须具有来源 URL 与观察日期，不包含站内综合评分字段。
- Role Profile 只能引用 Capability。
- Atlas Relation 端点存在，至少连接一项 Evidence，类型、方向性、状态与标签来自受限枚举或 taxonomy。
- 确定性历史关系出现时间倒置时必须有明确解释，否则构建失败。
- Atlas Theme 只能引用统一 taxonomy 标签，不能拥有、复制或删除节点与边；边的主题匹配读取 Relation 自己的标签，不从视觉邻近推断。

## 10. 路由与兼容

- `/map/`：能力地图
- `/careers/`：职业方向
- `/resources/`：成长资源
- `/resources/topics/[id]/`：主题资源集合
- `/sources/[id]/`：Source 与其 Work Item
- `/capabilities/[id]/`：能力详情
- `/topics/[id]/`：知识议题详情
- `/atlas/`：全局 Innovation Atlas
- `/about/`：项目资料入口
- `/trails/[id]/`：兼容跳转到对应资源主题，不再呈现强制学习顺序

资源查询参数固定区分 `resourceTopic`、`knowledgeTopic` 与 `capability`，不使用含义不明的 `topic`。

所有路由必须在 `/Learn-About-Games/` 基础路径下验证。

## 11. 失败处理

- 外部链接失效时保留记录与最后检查日期，清楚标注不可用，不静默删除历史内容。
- 翻译或访问条件不明时只展示已确认信息。
- 外部评价数据过旧时显示观察日期，不自动刷新或隐藏。
- 资源筛选没有结果时保留筛选条件并说明如何放宽，不回退成误导性的全部结果。
- 地图引用断裂、Atlas 关系无端点或无证据时构建失败。
- JavaScript 不可用时保留地图大纲、资源清单、Atlas 时间与关系说明。
- 主题存储损坏时回退跟随系统；个人状态继续回退安全空状态。

## 12. 测试与验收

### 12.1 自动测试

- 新数据结构与引用不变量的 Vitest 测试。
- 五项一级导航、About 二级入口和 Pages 基础路径 E2E。
- 所有 Capability 与 Knowledge Topic 详情可达。
- 地图实体、地域与关系具有不同 DOM 语义；自动测试验证全局节点锚点位于所属地域内，并验证关系端点与节点锚点对齐。
- Career Lens 应用后高亮数量、摘要和节点状态同步；个人状态保持独立。
- Resources 不渲染站内质量 badge、质量字段或由外部观察驱动的排序；透明度说明可以明确写出“本站不评分”。
- 资源主题、能力、媒介、语言和访问方式筛选正确，history 返回后重放状态。
- Atlas 默认始终渲染全局节点与边；主题切换不改变总数。
- Atlas 的节点类型、关系方向性、标签匹配、证据和年份范围正确；范围节点显示起止 span，Game 只显示单一年份。
- 系统、浅色、深色三态选择、持久化、无效值回退和无 JS 降级；系统浅色、系统深色、显式浅色覆盖深色系统、显式深色覆盖浅色系统均有浏览器验收。

### 12.2 视觉验收

至少在 1440px 与 320px 检查首页、能力地图、职业方向、资源库、Innovation Atlas 与 About：

- 无横向溢出。
- 桌面地图可一眼辨认地域、节点和连接，不再读成两列卡片。
- 职业透镜应用前后有明显但非评分式的差异。
- 100 项以上资源仍能通过主题和筛选快速缩小范围。
- Atlas 可以沿同一节点连续追踪分支关系，不再重复阅读关系卡片。
- 浅色与深色均满足 WCAG AA，键盘焦点清楚。
- 减少动态效果偏好下没有依赖动画才能理解的信息。

### 12.3 对抗性审查

发布前必须主动寻找：

- 任何把职业画像或个人状态变成分数的表达。
- 任何把资源收录状态伪装成质量认证的表达。
- 任何把主题高亮误实现为裁切 Atlas 子图的行为。
- 任何没有语义却为画面好看而添加的地图或历史连线。
- 任何让时间顺序看起来像因果关系的布局。
- 任何只靠颜色区分实体、关系或状态的设计。
- 任何为了数量目标而保留重复、不可核查或无法归类的资源。

## 13. 实施阶段

### 阶段 A：产品基础与语义迁移

完成数据 schema、导航、About、主题系统、旧路径降级与公共文档同步。

### 阶段 B：地图与职业方向

扩充地图节点与关系，完成桌面地域图、移动大纲、三个职业透镜和通用详情页。

### 阶段 C：资源扩充

建立统一资源目录与筛选，完成至少 12 个主题和约 100-150 项真实资源的录入、链接与语言核查。

### 阶段 D：创新时间网络

把现有 Roguelike 数据迁入全局图，补充 Metroidvania 与跨主题上下文，完成网络、高亮与证据详情。

### 阶段 E：全量验收与发布

完成构建、单元测试、桌面与移动 E2E、双主题视觉检查、链接抽检、连续性文档、Devlog、GitHub Pages 部署和线上复核。

## 14. 明确不做

- 不建立站内评分、星级或排行榜。
- 不建立统一学习课程或强制学习顺序。
- 不根据资源数量计算能力重要性。
- 不生成职业匹配分或个人完成率。
- 不使用无约束力导图决定节点位置。
- 不实时抓取第三方平台评价或引入运行时网络请求。
- 不建立账号、云同步、评论系统、后台数据库或 CMS。
- 不声称 v0.2 已完整覆盖所有游戏开发岗位或全部游戏创新史。
